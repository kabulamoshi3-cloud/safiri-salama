# SkyRex complete payment service

All 13 required endpoints are present and the migration creates all four tables idempotently. The design centres on a single `POST /pay` dispatcher that branches by `context` before reaching a shared `creditPayee()` helper and four provider webhook handlers. The `transfer` and `bill` contexts are handled inline before the mobile-money STK branch, and `wallet`/`cash` each get their own atomic path. Provider integrations are console-log stubs with documented real-API shapes, which is expected at this stage.

**Watch for:**
- Webhook endpoints accept any caller with no signature verification — **confirmed** HMAC/IP guard is absent; a forged callback can mark any transaction completed.
- Self-service `/refund` credits the wallet unconditionally without reversing the payee split — **confirmed** over-refund on wallet-paid rides.
- QR pay hard-codes an 80% driver credit instead of using `creditPayee()` — **confirmed** divergence from all other ride-payment paths.
- `transfer` fee rate is declared as 0.01 (1%) but the comment says "no extra fee" — **confirmed** contradiction between spec and code.

**Verdict**: NEEDS_CHANGES

## High-level view

All 13 required endpoints are registered and the migration SQL uses `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` throughout. `context_id` is stored as `UUID` in the schema but the code passes it as a raw string value from `req.body`; if callers send non-UUID strings this will produce a Postgres type error at runtime.

The four webhook handlers (mpesa, airtel, tigo, halotel) parse provider-specific field names and converge on `handlePaymentSuccess` / `handlePaymentFailure`. None of them validate the caller's origin or verify any HMAC/signature; the webhook endpoints are open to anyone who can POST to the server.

`creditPayee()` now accepts a `reference` parameter and writes both the payee split and the platform split to `payment_splits`. The wallet path inside `POST /pay` and `handlePaymentSuccess` both call it, with one exception: `POST /qr/pay` does its own inline 80 % driver credit and never calls `creditPayee()`, skipping the split record and applying a different fee rate than the 20 % defined in `PLATFORM_FEE_RATES.ride`.

The `transfer` context records debit/credit transaction rows and writes a split, but the 1 % fee contradicts the spec requirement of "no extra fee" for transfers.

Both admin endpoints (`/admin/refund`, `/admin/report`) gate on `user?.role === 'admin'`. The self-service `/refund` has a balance-sheet hole: it credits the user's wallet for the full amount but never reverses the payee credit that was written by `creditPayee()` at payment time, so the sum of wallet balances increases on every refund.

<details>
<summary>Issues (7)</summary>

1. **No webhook signature verification** — All four provider webhook endpoints (`/webhooks/mpesa`, `/webhooks/airtel`, `/webhooks/tigo`, `/webhooks/halotel`) accept any POST without verifying caller identity (HMAC, IP allowlist, or shared secret). A malicious actor can forge a success callback for any pending reference and mark arbitrary transactions as completed. Add provider-specific signature verification before processing any webhook body.

2. **Self-service refund does not reverse payee credit** — `POST /refund` credits the requester's wallet for the full amount but does not debit the payee wallet or update the `payment_splits` row written by `creditPayee()`. Every successful refund inflates total wallet balance by the payment amount. The refund path must debit the payee's wallet for their share and either delete or status-flip the corresponding split row, transactionally.

3. **QR pay bypasses creditPayee() and uses a wrong fee rate** — `POST /qr/pay` hard-codes a 80 % driver credit (`Math.round(qr.amount * 0.8)`) instead of calling `creditPayee(db, 'ride', ...)`. This skips writing any `payment_splits` row and applies a different rate than `PLATFORM_FEE_RATES.ride` (20 %). The admin settlement report will under-count ride splits generated via QR. Replace the inline credit with a `creditPayee()` call.

4. **transfer fee contradicts the spec** — `PLATFORM_FEE_RATES.transfer` is `0.01` (1%) and the transfer path explicitly deducts `fee = Math.round(amount * 0.01)` from the recipient's credit. The review criteria say "transfer context: debits sender, credits recipient, no extra fee." Either remove the fee rate or update the spec; right now code and spec disagree.

5. **context_id type mismatch** — The `transactions.context_id` column is `UUID` in the migration, but `req.body.context_id` is accepted as a raw string and passed directly to the query without coercion. If a caller sends a non-UUID string (e.g., an integer order ID), Postgres will throw an invalid-input-syntax error. Validate and/or cast `context_id` to UUID before inserting.

6. **Status polling expiry races the webhook** — The `GET /status/:reference` handler updates the transaction to `'expired'` using `database.query` (the pool singleton, outside a transaction) if `expires_at` has passed. If a provider webhook fires at exactly the same moment, the webhook's `handlePaymentSuccess` first checks `tx.status === 'completed'` — but if the poller wins the race and sets `'expired'` first, the webhook will still call `handlePaymentSuccess` and overwrite `'expired'` with `'completed'`, leaving the user with a duplicated credit. The expiry write should also use `FOR UPDATE` or a conditional `WHERE status = 'pending'`.

7. **Admin report recent_transactions leaks unmasked phone numbers** — The `recentResult` query fetches `u.phone AS user_phone` and the response includes a `user_phone_masked` field, but the spread `...tx` also surfaces the raw `user_phone` from the query row. Remove `user_phone` from the SELECT or explicitly project only the masked field.

<details>
<summary>Details</summary>

### Webhook endpoints — no caller authentication

All four webhook routes (`/webhooks/mpesa`, `/webhooks/airtel`, `/webhooks/tigo`, `/webhooks/halotel`) reach `handlePaymentSuccess` after parsing a few fields from `req.body`. There is no HMAC check, no IP allowlist, and no shared-secret header validation. The M-Pesa reference is taken directly from `req.body.output_ThirdPartyConversationID ?? req.body.reference`; an attacker who knows or guesses a valid pending reference can POST a success callback and trigger wallet credits. Every production mobile money integration ships a signature verification step — Vodacom TZ uses an HMAC-SHA256 on the raw body, Airtel uses an `X-Signature` header. These checks belong before any business logic runs.

### Self-service refund balance sheet hole

`POST /refund` runs this sequence inside a transaction:
1. `UPDATE wallets SET balance = balance + amount WHERE user_id = payer`
2. Mark original transaction `refunded = true`
3. Insert a `credit/refund` transaction row

Step 1 puts the money back in the payer's wallet. But when the original payment completed, `handlePaymentSuccess` called `creditPayee()`, which did `UPDATE wallets SET balance = balance + payeeAmount WHERE user_id = payee` and wrote a `payment_splits` row with `status = 'paid'`. The refund path never touches the payee wallet or the split row. Net result: the payee keeps their money, the payer gets a full refund, and total wallet supply grows by `payeeAmount` on every refund. The fix is to debit the payee's wallet for their share and mark the split reversed inside the same refund transaction.

### QR pay diverges from the ride payment path

The `POST /qr/pay` transaction path credits the driver wallet inline:

```typescript
await db.query(
  `INSERT INTO wallets ... VALUES ($1,$2,'TZS')
   ON CONFLICT (user_id) DO UPDATE SET balance = wallets.balance + $2`,
  [qr.driver_id, Math.round(qr.amount * 0.8)]
);
```

`creditPayee()` is not called, so no row is written to `payment_splits`. The `GET /admin/report` query for `pending_splits` and `total_platform_fees` will miss every QR-initiated ride, understating platform fee accrual.

### transfer fee vs spec

`PLATFORM_FEE_RATES.transfer = 0.01` and the code computes `fee = Math.round(Number(amount) * feeRate)`, deducting it from `netAmount` before crediting the recipient. The review criteria explicitly state "transfer context: debits sender, credits recipient, no extra fee." One of these must change — if the business decision is to charge 1%, update the spec; if it's zero-fee, set the rate to `0.00`.

### context_id UUID coercion

```sql
context_id UUID,  -- trip_id / order_id / etc.
```

The INSERT in the STK push branch passes `context_id ?? null` directly as a parameter. PostgreSQL will cast a string that looks like a UUID without complaint, but an integer or slug string will throw `ERROR: invalid input syntax for type uuid`. Add a guard: either validate with a UUID regex at the route level or cast to `::uuid` in the query.

### Status polling race with expiry

`GET /status/:reference` detects expiry and fires an update outside a transaction:

```typescript
await database.query(
  `UPDATE transactions SET status = 'expired' WHERE reference = $1`,
  [reference]
);
```

`handlePaymentSuccess` reads the transaction with `FOR UPDATE` but only skips processing if `tx.status === 'completed'`. If the poller sets `'expired'` between the `SELECT FOR UPDATE` inside `handlePaymentSuccess` and the final `UPDATE ... SET status = 'completed'`, the webhook wins the lock and overwrites `'expired'` with `'completed'`, triggering a second `creditPayee()` call on an already-credited payee. The expiry update should add `AND status = 'pending'` so it cannot overwrite an in-flight webhook transaction.

### Admin report phone leak

```typescript
recent_transactions: recentResult.rows.map(tx => ({
  ...tx,                         // includes raw user_phone
  amount_formatted: ...,
  user_phone_masked: maskPhone(tx.user_phone ?? ''),
}))
```

The spread copies every column from the query result, including the unmasked `user_phone`. Admin reports are often exported to spreadsheets or forwarded to finance teams. Either drop `user_phone` from the SELECT clause or explicitly construct the response object without spreading.

</details>
