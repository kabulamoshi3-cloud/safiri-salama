# Test and Documentation Implementation for Safiri Haraka API Gateway

Added 65 backend tests covering auth, tracking, and payments routes. Updated README.md and created SETUP.md to replace aspirational architecture documentation with accurate current-state docs. The test suite passes 57 of 65 tests; 8 failures trace to a JWT token field mismatch.

**Watch for:** JWT token field inconsistency between auth middleware (`userId`/`userType`) and route handlers (`id` in payments, `userId` in tracking/auth) — *confirmed*. Response field transformation in auth.ts missing `userType` mapping from DB `user_type` column — *confirmed*. Documentation claims README.md no longer references unbuilt services (Go fleet-tracker, Python AI, Kafka), but those references remain present in the "Planned Future Architecture" section — *likely*.

**Verdict**: NEEDS_CHANGES

## High-level view

The JWT helper correctly diagnoses the token field inconsistency: `authMiddleware` sets `req.user = { userId, userType }` but payments.ts reads `user.id`, creating a guaranteed null-dereference. The tracking and auth routes read `user.userId`, so they match the middleware. The fix is straightforward but gating: either change the middleware to also populate `id`, or change payments.ts to read `userId`.

The auth route returns `user_type` from the database but the test expects `userType` in the response. The register and login handlers don't transform the DB column name to camelCase, so the test assertion fails. This is a cosmetic inconsistency, not a logic bug, but it breaks 5 test cases.

Test coverage is solid for the happy path and common validation failures. The mocking strategy is sound: `pool.query` for auth/tracking (simple SELECT/UPDATE), `database.getClient()` for payments (transaction-based). Missing: concurrent transaction conflict tests for payments, GPS validation edge cases for tracking, and any test of the PATCH /me or change-password failure modes beyond wrong-password.

The documentation accurately describes the Node.js-only implementation and correctly identifies planned-but-not-built services in a separate section. However, the brief claims these references were removed, and they're still present. The SETUP.md is thorough, step-by-step, and targets a developer who has never touched the codebase. No false prerequisites (Go, Kafka, Python), accurate troubleshooting section.

## JWT token field mismatch between middleware and route handlers

The test helper's comment is accurate: `authMiddleware` sets `req.user = { userId, userType }` (line 47 of middleware/auth.ts), but payments.ts reads `(req as any).user.id` (line 125, line 167). The tracking routes read `(req as any).user?.userId` (line 180 of tracking.ts), which matches. The auth routes manually verify the JWT and read `decoded.userId` (line 165 of auth.ts), which also matches.

This means every payments route that accesses `user.id` gets `undefined`, which would cause DB queries to fail with "invalid UUID" or return empty results. The test suite mocks the DB, so it doesn't catch this — the test for `GET /payments/info` passes because the mock doesn't enforce that `user.id` must be a valid UUID, and the subsequent `db.query` call is mocked to return a row regardless.

The fix: change all `user.id` reads in payments.ts to `user.userId`, or extend `authMiddleware` to set both `id` and `userId`. The latter is more robust if other routes also expect `id`, but it's redundant. Grep for `user.id` in all route files to find the full blast radius.

## Auth response field transformation gap

The register and login handlers return the raw DB row, which has `user_type` (snake_case DB column). The tests expect `userType` (camelCase). This breaks 5 test assertions in auth.test.ts:

- `POST /register` expects `userType: 'passenger'`, gets `user_type: 'passenger'`
- `POST /login` expects `userType: 'passenger'`, gets `user_type: 'passenger'`
- (3 more in the login failure cases where the response is checked)

The fix: transform the DB row before returning it. Either destructure and rename (`const { user_type: userType, ...rest } = user; return { userType, ...rest }`), or use a mapping function if there are many fields. The same issue likely affects other routes that return user objects; check trips.ts, drivers.ts, ratings.ts.

## Auth route mounting inconsistency

The `/me`, `PATCH /me`, and `/change-password` routes are mounted at `/api/v1/auth`, which sits **outside** the `authMiddleware` guard (line 62 of index.ts mounts `/api` with authMiddleware, but `/api/v1/auth` is mounted separately at line 59). This forces these routes to manually verify the JWT (lines 149-165 of auth.ts). The test suite can't exercise them against the real app because `req.user` is never populated, so it builds a stub harness (`buildAuthApp`) that manually injects `req.user`.

This is architecturally inconsistent. The `/me` routes are authenticated endpoints that operate on the current user's data, so they should sit behind `authMiddleware` like every other authenticated route. Consider:

1. Move them to `/api/v1/user/me`, `/api/v1/user/profile`, or `/api/v1/profile` and mount that under `/api` (behind authMiddleware).
2. Or, mount `/api/v1/auth/me` under `/api` (but that's confusing since `/api/v1/auth/register` is public).

The current approach works but is surprising to maintainers and requires test harness workarounds.

## Documentation accuracy — planned services still present

README.md has a "Planned Future Architecture" section (lines 21-28) listing Go fleet-tracker, Python AI, Kafka, TimescaleDB, Elasticsearch. The section is clearly labeled as planned, not current. If the brief's intent was to remove all mention of these, it's incomplete. Decision: if the goal is to avoid aspirational docs entirely, delete the section. If the goal is to distinguish current from future, the current structure is fine.

## Mock strategy and release verification gap

The payments tests don't verify that `db.release()` is called. If a route handler forgets to release the client (or hits an early return before the release), the pool leaks. Consider adding `.toHaveBeenCalled()` assertions on `mockClient.release` in the happy-path tests.

## JWT helper dual-token workaround

`signRouteToken` includes both `id` and `userId` (plus `type`/`userType`/`phone`) because the auth routes read `userId` while payments reads `id`. `signAuthToken` signs the minimal shape `{ id, type, phone }`. This dual-helper approach is a workaround for the field inconsistency. Once the payments.ts field mismatch is fixed, `signAuthToken` could be removed.

## SETUP.md missing test note

SETUP.md could note that `npm test` requires no live DB (all tests use mocks), which is helpful for CI/CD environments or developers who want to run tests before setting up Postgres.

If the intent is to remove all mention of unbuilt services, this section should be deleted.
