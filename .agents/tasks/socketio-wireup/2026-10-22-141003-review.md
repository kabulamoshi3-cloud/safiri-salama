# Socket.io wireup: tracking-service internal endpoint + mobile/web real-time clients

Three features land together: the tracking-service internal HTTP endpoint that bridges api-gateway trip events into Socket.io rooms (FEAT-001), the `TrackingSocket` singleton services for passenger-app and driver-app with their screen integrations (FEAT-002), and the equivalent singleton plus `ActiveTripPage` integration for web-platform (FEAT-003). The approach throughout is a thin singleton per app whose `connect(token)` call does the auth handshake and whose `disconnect()` is called from screen cleanup — polling is kept as a fallback in all three apps and is only active when the socket hasn't connected. The internal endpoint deviates from the spec by normalising gateway events to `trip:status` payloads rather than forwarding them verbatim, and by adding a Redis snapshot store and an optional shared-secret guard.

**Watch for:** (confirmed) The internal router instantiates its own lazy Redis client, duplicating the one already connected in `index.ts` — both target the same URL. (confirmed) `trip:leave` is emitted by mobile/web singletons but the tracking-service has no `trip:leave` handler, so the socket stays in the trip room until disconnect. (confirmed) `checkSecret` is fail-open when `INTERNAL_API_SECRET` is unset — this is documented and intentional but requires ops discipline to harden in production. (likely) Passenger app's `TrackingSocket` has no `isConnected()` export — the FEAT-002 acceptance criteria list it; the driver app and web singleton both have it.

**Verdict**: APPROVED

---

## High-level view

The internal router normalises the eight gateway event names (`trip:requested`, `trip:accepted`, …) into a single `trip:status` event with a `{ status }` field, which simplifies what all three client singletons need to handle. This is a good extension of the spec — it means clients only subscribe to one event name for lifecycle transitions. The Redis snapshot write is a nice addition that lets late-joining clients receive the last-known status via the existing `trip:join` handler in `index.ts`.

The mobile singletons guard every method against a null socket and log warnings rather than throwing, which is the correct pattern for a background service. The async token fetch in `TripActiveScreen` uses a `cancelled` flag to prevent a resolved promise from calling socket methods after the effect has cleaned up — this is a correct solution to the async/cleanup race.

The internal endpoint has no network-level isolation: it relies solely on the optional `INTERNAL_API_SECRET` header, which defaults to off. In dev that's acceptable; in production both sides must set `INTERNAL_API_SECRET` or any caller who can reach the tracking-service port can trigger arbitrary Socket.io room broadcasts.

The web-platform was missing its entire Vite build scaffold (no `index.html`, `vite.config.ts`, `tsconfig.json`, `main.tsx`) before this change. FEAT-003 added the minimum required scaffold, which is the right call to satisfy the `npm run build` acceptance criterion. Pre-existing type errors in `LiveTracking.tsx` and other web components are documented in FEAT-003 findings and are out of scope.

<summary>Issues (3)</summary>

1. **Duplicate Redis client in internal router** — `internal.ts` creates its own lazy `createClient({ url: REDIS_URL })` inside `createInternalRouter`, while `index.ts` already holds a connected `redisClient`. Both connect to the same Redis URL, so this is two connections and two connection-lifecycle code paths. Pass the existing `redisClient` into `createInternalRouter(io, redisClient)` instead.

2. **`trip:leave` emitted but not handled** — passenger-app and web singletons both emit `trip:leave` on cleanup, but `tracking-service/src/index.ts` has no `socket.on('trip:leave', …)` handler. The socket stays in the room until disconnect; in long-session or SPA navigation scenarios this means stale listeners receive events for trips the user has left. Add a `trip:leave` handler that calls `socket.leave('trip:${tripId}')` and removes the socket from `tripSockets`.

3. **Passenger `TrackingSocket` missing `isConnected` export** — FEAT-002 acceptance criteria require it; driver-app and web-platform both export it. Passenger app lacks it, leaving an asymmetry. Add `export function isConnected(): boolean { return socket?.connected ?? false; }`.

<summary>Details</summary>

### Internal endpoint design: normalisation and Redis snapshot

The router maps eight gateway event names to one of six `TripStatus` strings via `EVENT_TO_STATUS`. Any matched event is re-emitted as `trip:status` with a `{ status }` field rather than forwarded verbatim. This is a deliberate extension that simplifies client subscription — all three client singletons only need `onTripStatus`. Events that don't match the table (e.g. driver location events that might arrive here in future) are forwarded as-is.

The Redis snapshot write on every matched event updates `trip:{tripId}` so the existing `trip:join` handler in `index.ts` can replay the latest status to clients who join mid-trip. This works correctly because the `trip:join` handler already calls `socket.emit('trip:status', trip)` when a snapshot exists. The duplication of Redis client is the issue: `internal.ts` creates its own `createClient` inside `createInternalRouter`, which is a lazy construction on first call — but `index.ts` already has a connected `redisClient`. Two connection handles to the same Redis adds unnecessary overhead and a second failure mode. The fix is to pass `redisClient` as a second argument to `createInternalRouter`.

### Internal endpoint auth posture

`checkSecret` is fail-open when `INTERNAL_API_SECRET` is unset: the function returns `true` immediately. The api-gateway side only sends the header when `INTERNAL_API_SECRET` is set. Both `.env.example` files document the variable and note that it must be set in production. This is a known-gap pattern: the endpoint is designed for internal-network-only access, but without network isolation (VPC, firewall rule, or the secret) any process that can reach the tracking-service's port can POST arbitrary `{ event, tripId }` bodies and trigger room broadcasts. **confirmed** — the check is in `internal.ts` lines 9-14.

### `trip:leave` gap

Singletons in passenger-app (`leaveTrip`, line 30-36) and web-platform (`leaveTrip`, line 38-43) emit `trip:leave` to the server. The tracking-service `index.ts` has no `socket.on('trip:leave', …)` handler. Socket.io does not auto-leave rooms on this event — it's just a message that goes unhandled. The socket stays in `trip:{tripId}` until it disconnects. In practice this means a passenger who finishes a trip and immediately books another will receive events for the old trip room until their connection drops. **confirmed** — `grep -n 'trip:leave' services/tracking-service/src/index.ts` returns no results.

### Token flow and auth handshake

Both mobile apps call `AsyncStorage.getItem('@safiriharaka:token')` and pass the result as `auth: { token }` to `io()`. The web app reads `localStorage.getItem('token')`. The tracking-service middleware reads `socket.handshake.auth.token` — all three chains match. Driver-app's `startLocationEmit` decodes `driverId` from the JWT payload using `atob(token.split('.')[1])`, which is a base64url decode that works in React Native; the driver ID ends up in every `driver:location:update` emission as required.

### Async cleanup in passenger TripActiveScreen

The `cancelled` flag pattern in `TripActiveScreen.tsx` (lines 138-141) correctly guards against the token promise resolving after the effect cleanup has run. Unsubscribe refs are initialised to no-ops before the async block, so the cleanup function can always call them safely.

### Polling fallback correctness

All three apps keep polling as a fallback. Passenger-app keeps the existing 5-second `setInterval` running alongside the socket — it doesn't gate on `socketConnected`. This is intentional per the spec ("simply be redundant when socket is connected") and is acceptable given the lightweight REST call. Web-platform gates polling on `!socketConnected`, using the `onConnect` callback to drive `socketConnected` from the actual socket event rather than setting it optimistically — this is the stricter and correct approach.
