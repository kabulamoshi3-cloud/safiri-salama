# Socket.io wireup for real-time trip tracking across gateway, mobile, and web

Wires a tracking-service internal HTTP endpoint that re-broadcasts api-gateway trip events into Socket.io trip rooms, and adds socket.io-client singletons to the passenger, driver, and web apps alongside their existing REST polling. The server side is intentionally left untouched except for a new `internal.ts` router mounted at `/api/internal`; all client work is consumer-side singletons that connect with `auth: { token }`, join a trip room, and register listeners for `driver:moved`, `trip:status`, and `eta:changed`. The structural checklist holds: socket.io-client@4.7.5 is pinned in all three package.json files, token keys match (`@safiriharaka:token` mobile / `localStorage 'token'` web), the handshake auth matches the existing `io.use()` middleware, and intelligence.ts, safety.ts, and the Socket.io event handlers are unmodified.

**Watch for:** the real-time status push that is the whole point of this wireup does not reach clients. The clients subscribe to `trip:status`, but the gateway broadcasts `trip:accepted`/`trip:started`/etc. under those exact names with no `status` field, and the `trip:join` snapshot the clients also expect is empty because nothing emits `trip:start` to populate Redis. On the web this is compounded by an optimistic `socketConnected` flag that suppresses the polling fallback before the socket has connected.

**Verdict**: NEEDS_CHANGES

## High-level view

**Trip-status event contract is broken end-to-end.** The internal endpoint forwards the gateway's event name verbatim (`trip:accepted`, `trip:started`, …) into the trip room, but every new client listens for `trip:status` and reads a `status` field off the payload. The gateway payloads carry no `status` field, and the tracking-service's own `trip:status` snapshot (emitted on `trip:join`) is empty because no client emits `trip:start` to populate Redis. The net effect is that server-driven status transitions never update any client; the passenger screen is frozen at `'searching'` with no REST status fetch to recover it, and the web is frozen at its initial REST snapshot.

**Web polling fallback is dead on arrival.** `ActiveTripPage` sets `socketConnected = true` synchronously right after `connect()`, before the WebSocket has connected, and never clears it on `connect_error`. The polling effect is gated on `!socketConnected`, so a failed or slow handshake leaves the trip with neither socket updates nor polling.

**Passenger listener lifecycle leaks.** Listeners are registered inside an async `AsyncStorage` callback whose cleanup closure captures no-op unsub functions when the effect re-runs before the promise resolves, leaving orphaned listeners on the module singleton. The passenger also never calls `disconnect()` (only `leaveTrip()`), unlike the web and driver apps, so the socket outlives the screen and stale listeners carry into the next trip.

**Internal endpoint is an unauthenticated trust boundary by design.** `/api/internal/trip-event` has no auth and forwards any event name to any trip room; the FEAT spec calls this intentional (same private network), but anyone reachable on the tracking-service port can broadcast arbitrary events into any trip.

**Unrelated i18n changes are bundled into the mobile commit.** `TripActiveScreen.tsx` gained `i18n.t()` string replacements and an `i18n.subscribe` re-render hook that have nothing to do with Socket.io.

The one real-time stream that works end-to-end is driver position — the driver emits `driver:location:update`, the server computes ETA and broadcasts `driver:moved`, and the passenger's `onDriverMoved` reads the matching fields — which is the proof the wiring can be consistent and makes the status gap a contract problem rather than a plumbing one.

### Trip-status event contract mismatch (confirmed)

The internal router is intentionally generic: it reads `{ event, tripId, ...data }` and does `io.to(\`trip:${tripId}\`).emit(event, { tripId, ...data })`. The `event` value comes straight from api-gateway's `notifyTrackingService`, which sends `trip:requested`, `trip:accepted`, `trip:driver_arriving`, `trip:arrived`, `trip:started`, `trip:completed`, and `trip:cancelled` — never the literal string `trip:status`.

Every new client subscribes to `trip:status`:

```
passenger  TrackingSocket.onTripStatus  ->  socket.on('trip:status', cb)
web        trackingSocket.onTripStatus   ->  socket.on('trip:status', cb)
```

and both handlers consume a `status` field:

```
passenger:  if (trip.status) setStatus(trip.status as TripStatus)
web:        setTrip(prev => prev ? { ...prev, status: updatedTrip.status } : prev)
```

The gateway payloads don't carry one — `trip:accepted` arrives as `{ tripId, driverId }`, `trip:started` as `{ tripId }`, `trip:completed` as `{ tripId, final_fare }`. So even if the event names matched, the `if (trip.status)` guard would no-op.

The only place the tracking-service itself emits `trip:status` is the `trip:join` handler, which reads the trip from Redis and emits it if present. Nothing in the new client flow populates that Redis key: it is written only by the tracking-service `trip:start` socket handler, and the driver-app's `TrackingSocket` never emits `trip:start` (it emits `driver:location:update`, `trip:join`, `trip:leave`). So the `trip:join` snapshot is empty, and `onTripStatus` never fires at all — not the initial snapshot, not the transitions. The same missing Redis entry means the traffic monitor never starts, so `eta:changed` — the third event the clients subscribe to — is likewise inert.

The passenger screen initializes `status` to `'searching'`, has no REST trip-status fetch, and its 5-second poll fetches driver-location only. So for a real trip the passenger is frozen at `'searching'`: the driver accepts, the gateway emits `trip:accepted` into the room, the passenger's socket receives it, and there is no listener for it. The web is slightly better off because `ActiveTripPage.load()` fetches `/trips/${tripId}` up front and sets the initial status from REST — but then it never advances.

The FEAT specs are internally inconsistent here: FEAT-001's acceptance criterion explicitly asserts the endpoint emits `trip:accepted` (the forwarded event name), while FEAT-002/003 have clients listen for `trip:status`. One side has to give.

### Web polling fallback suppressed by an optimistic flag (confirmed)

`ActiveTripPage` sets `socketConnected` optimistically:

```
trackingSocket.connect(authToken);
trackingSocket.joinTrip(tripId!);
setSocketConnected(true);          // before the socket has connected
```

`connect()` returns immediately; the actual handshake is async. `setSocketConnected(true)` runs before `connect` or `connect_error` fires, and nothing in the page listens for those events to correct the flag — the singleton only `console.log`s them. The polling effect guards on it:

```
if (socketConnected || !tripIsActive) return;   // polling suppressed
```

So if the handshake fails or stalls, the page has no socket updates (per the contract gap above) and no polling. The `trackingSocket.isConnected()` helper exists but is unused; the flag should be driven by real connect/disconnect events rather than set before the connection attempt completes.

### Passenger listener lifecycle leak and missing disconnect (confirmed)

Listener registration in `TripActiveScreen` happens inside `AsyncStorage.getItem('@safiriharaka:token').then(...)`:

```
let unsubMove = () => {}; let unsubStatus = () => {}; let unsubETA = () => {};
AsyncStorage.getItem(...).then(token => {
  ...
  unsubMove  = TrackingSocket.onDriverMoved(...);
  unsubStatus= TrackingSocket.onTripStatus(...);
  unsubETA   = TrackingSocket.onETAChanged(...);
});
...
return () => { unsubMove(); unsubStatus(); unsubETA(); TrackingSocket.leaveTrip(); ... };
```

The effect deps include `status`, so on every status transition the effect cleanup runs and re-registers. If cleanup runs before the AsyncStorage promise resolves — the common case on a fast status change — the unsub functions are still the initial no-ops, the old listeners are never removed, and the `.then` then registers fresh listeners on the singleton that no cleanup reference points to. They accumulate across the trip.

Compounding this, the passenger cleanup calls `TrackingSocket.leaveTrip()` but never `TrackingSocket.disconnect()` — unlike the web and driver apps, which both disconnect on unmount. `connect()` is idempotent (`if (socket?.connected) return`), so the socket persists after the screen unmounts and the orphaned listeners survive into the next trip, where they fire against the wrong trip's data.

### Unauthenticated internal trip-event endpoint (confirmed)

`createInternalRouter` mounts `POST /trip-event` with no auth guard, by FEAT-001's design ("internal only — caller is api-gateway on the same private network"). The handler forwards any `event` string to any `trip:${tripId}` room, so anyone who can reach the tracking-service port can broadcast arbitrary events — a forged `trip:completed`, a fake `driver:moved`, or any custom event name — into any trip room. This is a deliberate trade-off documented in the spec, but it is a trust boundary worth minimal hardening: a shared-secret header checked by the router, or binding the internal route to localhost, would close the gap without touching the consumer side.

### Unrelated i18n changes bundled (confirmed)

`TripActiveScreen.tsx` carries a full i18n pass — `import i18n from '../i18n'`, an `i18n.subscribe` force-update hook, and a dozen `i18n.t(...)` replacements of hardcoded strings across `cancelTrip`, `getStatusUI`, and the ETA/fare UI — committed inside `a273e93 feat(mobile): add Socket.io TrackingSocket`. None of it relates to the Socket.io wireup. It isn't harmful, but it muddies a diff whose scope is explicitly consumer-side real-time wiring; it belongs in its own commit.

### Test coverage

No tests exist or were added for any affected package (the context notes no test framework is configured for the apps, and the services have no suite for these files), so the FEAT verification rests on `tsc --noEmit` and the web `vite build` — both pass for the new code; the tracking-service's only `tsc` errors are four pre-existing ones in the forbidden `intelligence.ts`. What is not tested, and cannot be caught by type-checking, is the runtime event contract above; that gap is invisible to `tsc` and only surfaces when a real trip transition is observed not to update the client.
