# GPS ML Pipeline: Traffic Prediction Frontend and ML Service

Adds predictive traffic visualization to the passenger app and a standalone Python XGBoost service for speed prediction. The frontend calls two new endpoints (`/tracking/traffic/predict` and `/tracking/traffic/best-time`) with configurable departure offsets. The ML service provides model-based predictions but is never a hard dependency — the Node.js API gateway always falls back to SQL baseline when unavailable.

The implementation meets 19 of 20 specified acceptance criteria. One gap: the confidence label thresholds use `> 0.7` and `>= 0.4` instead of the more conventional `>= 0.7` and `>= 0.4`, creating a boundary where `confidence === 0.7` lands in the "wastani" bucket rather than "juu".

## High-level view

The traffic screen adds a three-button departure selector (`'Ondoka Sasa'`, `'+Dakika 30'`, `'+Saa 1'`) that re-fetches predictions whenever the offset changes. Predictions are fetched via `POST /tracking/traffic/predict` with `{ segment_ids, departure_time }` and color the map polylines from the `color` field with fallback to `STATUS_COLORS[seg.status]`. When the predict endpoint fails, the UI shows a `'Kutumia data ya zamani'` banner without clearing the map, preserving last-known data.

Confidence is computed as the mean across all prediction objects and bucketed into three Swahili labels (`'Utabiri wa juu'`, `'Utabiri wa wastani'`, `'Mfumo wa msingi'`). The boundary logic at 0.7 is off by one comparison operator: using `> 0.7` instead of `>= 0.7` means a model returning exactly 0.7 falls into the middle tier instead of the high tier.

Best-time recommendations are fetched from `GET /tracking/traffic/best-time` after a successful prediction. When `savings_minutes > 5`, a green card displays `'Ondoka HH:MM — okoa dakika N 🕒'` using the exact format specified.

The Python service exposes `POST /predict` and `GET /health`. The predictor loads the XGBoost model from `MODEL_PATH` and returns `None` when unavailable, which triggers a 503 response from FastAPI. The trainer reads `segment_speed_observations`, checks `MIN_TRAINING_SAMPLES`, trains XGBoost, and saves the model. All six required files exist and contain no syntax errors.

## Confidence threshold boundary

The confidence label logic computes the mean confidence across all prediction objects and buckets it into three tiers:

```typescript
const avgConf = preds.reduce((sum, p) => sum + (p.confidence || 0), 0) / preds.length;
if (avgConf > 0.7) setConfidenceLabel('Utabiri wa juu');
else if (avgConf >= 0.4) setConfidenceLabel('Utabiri wa wastani');
else setConfidenceLabel('Mfumo wa msingi');
```

The first condition uses `> 0.7` instead of `>= 0.7`. Standard ML confidence bucketing treats 0.7 as the boundary for "high confidence", meaning values `>= 0.7` should land in the top tier. As written, a model returning exactly `0.7` falls into the middle tier ("Utabiri wa wastani") instead of the high tier ("Utabiri wa juu").

This is a confirmed issue at line 124 of `TrafficScreen.tsx`. Change `avgConf > 0.7` to `avgConf >= 0.7` to align with typical confidence thresholding.
