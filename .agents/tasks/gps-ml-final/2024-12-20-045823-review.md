# GPS ML Pipeline: Traffic Prediction UI and Model Service

Adds ML-driven traffic prediction to the passenger app's traffic screen and implements the standalone Python training/prediction service. The screen now offers departure-time selection ("Ondoka Sasa", "+Dakika 30", "+Saa 1"), fetches predictions from the API, renders predicted road colors on the map, displays confidence labels, and shows a best-time recommendation card when savings exceed 5 minutes. The ml-service provides XGBoost-based speed prediction with graceful fallback to the SQL baseline when the model is unavailable.

**Watch for:** Missing TypeScript error verification (**confirmed**), no retry strategy when predict fails (**confirmed**), and the ml-service has no shared segment hash dictionary with trainer.py (**confirmed**).

**Verdict**: CHANGES_REQUESTED

## High-level view

The TrafficScreen departure selector uses hardcoded Swahili labels and triggers a new prediction on every offset change. Predictions paint polylines using the returned `color` field or fall back to `STATUS_COLORS` when no prediction exists. Confidence labels map average confidence to three Swahili tiers. The best-time card formats the recommendation as "Ondoka HH:MM — okoa dakika N 🕒" but only appears when savings exceed 5 minutes. When predict fails, the screen sets a cache banner and preserves the last successful predictions instead of clearing the map.

The ml-service exposes `/predict` and `/health`, loads the XGBoost model from disk on startup, and returns None (503) when the model is missing. The trainer reads from `segment_speed_observations`, honors `MIN_TRAINING_SAMPLES`, trains XGBoost with fixed hyperparameters, and saves the model to `MODEL_PATH`. The README explicitly states Node.js never depends on the service and falls back to SQL baseline. All six required files are present. Python syntax is valid.

The segment encoding in predictor.py uses `hash(segment_id) % 1000`, but trainer.py uses LabelEncoder, creating a semantic mismatch. Predictions will return values but they won't correspond to the segments the trainer learned. The passenger app criteria are fully met. The ml-service structure is correct but the encoding gap blocks meaningful predictions.

## Departure selector and prediction flow

The screen declares three buttons with exact labels `'Ondoka Sasa'`, `'+Dakika 30'`, `'+Saa 1'` that set `departureOffset` to 0, 30, or 60 minutes. A `useEffect` watches `[segments, departureOffset]` and calls `fetchPredict` whenever either changes. The predict request constructs `departure_time` by adding `departureOffset * 60000` milliseconds to `Date.now()` and posts to `/tracking/traffic/predict` with `{ segment_ids, departure_time }`. On success, predictions are stored and confidence is computed as the average of `p.confidence` across all predictions. On failure, `setUsingCache(true)` triggers the "Kutumia data ya zamani" banner and preserves the last predictions array.

## Polyline coloring and confidence labels

Each polyline queries `predictionFor(seg.segment_id)` to find a matching prediction. If found, it uses `pred.color`; otherwise it falls back to `STATUS_COLORS[seg.status]`. Confidence labeling maps `avgConf >= 0.7` to `'Utabiri wa juu'`, `>= 0.4` to `'Utabiri wa wastani'`, and anything lower to `'Mfumo wa msingi'`.

## Best-time recommendation card

After a successful predict, the screen fetches `/tracking/traffic/best-time?segment_ids=...&from_time=...`. If the response includes `savings_minutes > 5`, it stores `{ best_time, savings_minutes }` and renders a card positioned absolutely at the bottom of the map. The card text is:

```
Ondoka {formatBestTime(bestTime.best_time)} — okoa dakika {Math.round(bestTime.savings_minutes)} 🕒
```

`formatBestTime` calls `toLocaleTimeString([], { hour: '2-digit', minute: '2-digit' })`, producing "HH:MM" format.

## Segment encoding inconsistency

**Confirmed issue**: trainer.py uses `LabelEncoder().fit_transform(df["segment_id"])` to encode segments as integers 0, 1, 2, ... N-1 in the order they appear in the training data. predictor.py uses `abs(hash(segment_id)) % 1000` to encode segments at prediction time. These two encodings are incompatible. A segment with hash 342 will have that value passed to the model, but the model was trained on LabelEncoder indices that have nothing to do with hash values. Predictions will return numbers but they are meaningless.

The comment in predictor.py says "must match training; use 0 for unknown" but it does not match. The trainer does not save the LabelEncoder, so the predictor cannot use it. The simplest fix is to switch trainer.py to the same hash-based encoding used in predictor.py, or to pickle the LabelEncoder and load it in predictor.py.
